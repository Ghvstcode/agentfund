# Claude Code headless facts this package relies on

Verified on 2026-10-06 against the live documentation and against the
installed CLI (`claude` 2.1.289: `claude --help`, one real `claude -p` run on
the host, and a credential-less run inside `agentfund/sandbox:dev`). Re-verify
when bumping `CLAUDE_CODE_VERSION` in `images/sandbox/Dockerfile`.

Sources:

- <https://code.claude.com/docs/en/agent-sdk/cost-tracking> — usage/cost fields, de-duplication, placeholder `output_tokens`

## Invocation

```
claude -p --output-format stream-json --verbose --include-partial-messages \
       --dangerously-skip-permissions --setting-sources user \
       --strict-mcp-config --no-session-persistence [--model M]      < prompt
```

| Flag | Why | Verified by |
| --- | --- | --- |
| `-p` / `--print` | Non-interactive mode; exits 0 on success, non-zero on failure. | docs, `--help`, live run |
| prompt on **stdin** | `-p` with no prompt argument reads the prompt from stdin (docs: "Non-interactive mode reads stdin", capped at 10 MB). Chosen over an argv prompt so a prompt that starts with `--` or is very long is passed verbatim, and so it is not in the process list. | live run with a prompt starting with `--` |
| `--output-format stream-json` + `--verbose` | Newline-delimited JSON events. The docs always pair stream-json with `--verbose`. | docs, live run |
| `--include-partial-messages` | Adds `stream_event` lines. Needed because per-message `output_tokens` is only a placeholder; `message_delta` carries the real, growing output count, which is what lets the worker kill a run at `max_tokens` mid-response. | docs (cost-tracking), live run |
| `--dangerously-skip-permissions` | Nobody can answer permission prompts; `system/init` then reports `permissionMode: "bypassPermissions"`. `--help`: "Recommended only for sandboxes with no internet access". The sandbox is the boundary, not the CLI's permission system. | `--help`, live run on host and in the sandbox image as uid 10001 |
| `--setting-sources user` | Do not load `project`/`local` settings files from the repository being worked on. | `--help` (flag exists and is accepted); effect not separately tested |
| `--strict-mcp-config` | Ignore MCP server definitions other than `--mcp-config` (none), e.g. a repo's `.mcp.json`. | `--help`; accepted in live run |
| `--no-session-persistence` | Nothing to resume; the container is discarded. Print-mode only. | `--help`; accepted in live run |
| **not** `--bare` | Bare mode never reads `CLAUDE_CODE_OAUTH_TOKEN` (docs: "Bare mode does not read `CLAUDE_CODE_OAUTH_TOKEN`"), which would remove an authentication method. | docs |

Not verified by execution: the CLI refusing `--dangerously-skip-permissions`
when run as root (known behaviour; the worker always runs it as uid 10001).

## Credentials

- `CLAUDE_CODE_OAUTH_TOKEN`: "A long-lived OAuth token generated by `claude setup-token`"; one-year token for a Pro/Max/Team/Enterprise subscription, "can only make model requests".
- `ANTHROPIC_API_KEY`: sent as `X-Api-Key`; "In non-interactive mode (`-p`), the key is always used when present."
- Precedence when several are set (docs): cloud provider (`CLAUDE_CODE_USE_BEDROCK`/`_VERTEX`/`_FOUNDRY`) → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` → `apiKeyHelper` → `CLAUDE_CODE_OAUTH_TOKEN` → profiles → `/login` credentials.

The worker forwards **whichever of `CLAUDE_CODE_OAUTH_TOKEN` / `ANTHROPIC_API_KEY`
is set** in the donor's environment (both if both), plus any variable names
the donor lists in `sandbox.pass_env`, and lets the unmodified CLI choose. It
does not restrict or reorder the CLI's authentication methods. Values travel
only as `docker exec -e NAME` with the value in the docker CLI's process
environment — never in argv, image layers, config files, logs or reports.

With no credential at all the CLI does not fail at start-up; it emits
(verified in the sandbox image, no network):

```json
{"type":"assistant","error":"authentication_failed", ...}
{"type":"result","subtype":"success","is_error":true,"result":"Not logged in · Please run /login","total_cost_usd":0, ...}
```

Note `subtype` is `"success"` even though `is_error` is `true`: always test `is_error`.

## Metering rules (`meter.go`)

- `tokens_in` = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`; `tokens_out` = `output_tokens` (spec/manifest.md "Metering").
- Count each `message.id` **once** (docs: "all messages in that turn share the same ID, so deduplicate by ID").
- Per-message `output_tokens` is "the count the API had reported at `message_start`" — a placeholder (3 above, real value 43). The real value comes from `message_delta` while streaming, and from the `result` at the end.
- Sub-agent calls carry `parent_tool_use_id`; `message_delta` is attributed to the message started under the same parent.
- The final `result` wins when present: `modelUsage` summed over models (it "counts subagent requests alongside the top-level loop"; `usage` "counts only the top-level agent loop"), falling back to `usage`. This replaces the running sum, so nothing is counted twice.
- A zeroed `result` (docs: after a session crash "every cost field may be zeroed") does not replace the running sum.
- `cost_estimate` = `total_cost_usd`, a client-side estimate ("not authoritative billing data").

## Rate limiting and other provider refusals

| Signal | Source | Worker reaction |
| --- | --- | --- |
| `{"type":"assistant","error":"rate_limit"}` (or `"overloaded"`) | `SDKAssistantMessageError` (typescript reference) | rate limited |
| `{"type":"rate_limit_event","rate_limit_info":{"status":"rejected","resetsAt":…}}` | observed event type; `status:"allowed"` seen live, `"rejected"` inferred from the field's meaning — **not observed** | rate limited; `resetsAt` (Unix seconds) is the floor for the backoff |
| `{"type":"result","is_error":true,"api_error_status":429}` (or 529) | field observed (`null` on success); 429 value **not observed** | rate limited |
| `{"type":"system","subtype":"api_retry","attempt":n,"error":"rate_limit",…}` | headless docs, "Handle API retries" | the CLI retries by itself; treated as rate limited only after 3 consecutive retries with no successful call in between |
| `error` ∈ `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `cloud_credential_error`, or `api_error_status` 401/403 | docs + live (`authentication_failed`) | claim released, worker stops with a clear message |

Rate limited ⇒ the sandbox is torn down, the claim is **released** with the
tokens burned so far, an exponential backoff with jitter (5 min doubling to
4 h, never ending before `resetsAt`) is stored, and no task is claimed until
it ends.

## Network

- The CLI honours `HTTPS_PROXY`/`HTTP_PROXY` (and lowercase forms; first set wins in the order `https_proxy`, `HTTPS_PROXY`, `http_proxy`, `HTTP_PROXY`); no SOCKS. The sandbox sets all four to `http://egress-proxy:3128`.
- Required host for model requests: `api.anthropic.com`. That is the whole default egress allowlist (`sandbox.allow_git_host` and `sandbox.extra_allow_hosts` add to it).
- The docs list `platform.claude.com` for "OAuth token exchange, refresh, and revocation". Whether a long-lived `setup-token` token ever needs it at run time was **not tested** (it would need a real token and real usage). If a run under an OAuth token fails with an authentication error although the token is valid, add `platform.claude.com` to `sandbox.extra_allow_hosts`.
- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `DISABLE_AUTOUPDATER=1` are set so the CLI does not try telemetry/update hosts that the proxy would refuse anyway.
